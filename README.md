# Unity Mobile Starter

Internal Unity template for **SlipperyZlope Games**.

This repository is the reusable foundation for small mobile games. It standardizes project structure, Unity/editor settings, repository hygiene, and Codex rules without introducing gameplay systems before a game actually needs them.

## Status

**v0.2 — Unity bootstrap baseline**

## Baseline

- Unity: **6000.5.8f1**
- Language: **C#**
- Primary target: **Android**
- Secondary target: **iOS**
- Input package: **Unity Input System 1.20.0**
- Active Input Handling: **Input System Package (New)**
- Dynamic Batching: **disabled**
- Asset serialization: **Force Text**
- Version control mode: **Visible Meta Files**
- Orientation: decided per game
- Rendering pipeline: decided per game
- Repository model: one game = one repository generated from this template

## Principles

1. Keep the starter smaller than the games built from it.
2. Do not add game-specific mechanics to this repository.
3. Promote code back into the starter only after it proves reusable across multiple games.
4. Prefer simple, explicit C# over speculative frameworks.
5. Keep mobile performance and build constraints visible from the beginning.
6. Codex may implement most code, but architecture remains intentionally shallow and reviewable.
7. Generated Unity caches and local IDE state never belong in Git.

## What v0.2 includes

- canonical project folder layout and Unity-generated `.meta` files;
- Unity-specific `.gitignore` and repository text conventions;
- pinned Unity editor version;
- canonical Unity `ProjectSettings` baseline generated by the editor;
- Input System **1.20.0** plus `packages-lock.json`;
- legacy Input Manager disabled as the active input backend;
- Dynamic Batching disabled;
- Codex operating rules;
- architecture, new-game, and template-boundary documentation.

## What v0.2 deliberately does not include

- player controllers;
- runner, farming, crowd, merge, idle, combat, economy, or progression systems;
- ad SDKs;
- analytics SDKs;
- IAP integrations;
- save framework;
- service locator / dependency injection framework;
- generic `GameManager` hierarchy;
- URP configuration that every game would be forced to inherit;
- placeholder art or audio.

Those are added only when a real title requires them. Reusable pieces can later be promoted into a future starter version.

## Starting a new game

1. Create a new repository using this repository as a GitHub template.
2. Give the game repository its own name and history.
3. Clone the new repository locally.
4. Open it with Unity **6000.5.8f1**. Unity should rebuild local caches such as `Library/`; those are never committed.
5. Follow `docs/NEW_GAME_CHECKLIST.md` to replace template identity values and make game-specific platform decisions.
6. Create `docs/GAME_SPEC.md` before asking Codex to implement gameplay.
7. Keep changes specific to that title in its own repository.

`DefaultCompany` and `unity-mobile-starter` are template placeholders, not release identity. A generated game must replace them before its first real device/store build.

## Template rule

If a class, prefab, setting, or package exists only because one game needs it, it belongs to that game's repository — not here.

The starter should evolve through evidence, not prediction.
